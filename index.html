B. The 7 UML Relationship Arrows & Code Implementations

1. Generalization (Inheritance) ───▷

IS-A relationship between child class and parent class.

// Java
class Dog extends Animal {}
2. Realization (Interface) - - ▷

Implementation of an interface contract by a class.

// TypeScript
class CreditCard implements PaymentProcessor {}
3. Composition (Strong Ownership) ◆───

Part cannot exist without the Whole. Lifecycles are tied.

// C++
class Car { Engine engine; };
4. Aggregation (Weak Ownership) ◇───

HAS-A relationship. Part can exist independently of Whole.

// Java
class Department { List<Teacher> teachers; }
5. Direct Association ───>

One-way structural connection where Class A holds Class B.

// Java
class Customer { Order activeOrder; }
6. Simple Association ────

Bi-directional or general link between two class concepts.

// Concept
Student ──── Course
7. Dependency - - >

Temporary usage. Class A uses Class B as a method parameter.

// Java
void export(Printer p) { p.print(); }

Strict Level 0 Rules

  • Single Central Process: Named 0.0 representing the entire system as a black box.
  • NO Data Stores: Databases, files, or persistent stores MUST NEVER appear at Level 0. They are hidden inside the system circle.
  • External Entities: Rectangles representing sources (originators) and sinks (receivers) of data.

Level 1 DFD Shape Legend

Common Gane-Sarson and Yourdon-DeMarco notation for processes, stores, entities, and data flows.

1.0
Circle / Soft-Oval (Process)

Business operation or data transformation step, such as 1.0 Validate Order. Yourdon-DeMarco uses a circle; Gane-Sarson uses a rounded rectangle.

D1
Open Rectangle / Parallel Lines (Data Store)

Data at rest, such as databases, files, or tables. Identify stores with labels like D1 Users or D2 Orders.

DB
Cylinder (Database)

An actual relational or physical database storage system, commonly shown in architecture diagrams.

EXT
Solid Rectangle (External Entity)

A person, department, or external system outside the system boundary, such as Customer or Payment Gateway.

→
Arrow (Data Flow)

Data in motion. Every arrow should carry a clear label describing the data package being transferred.

Understanding Level 1 DFD Concepts

Process Numbering Rules

Sub-processes are numbered sequentially (e.g. 1.0, 2.0, 3.0). If a sub-process is exploded further into a Level 2 DFD, process 1.0 decomposes into 1.1, 1.2, 1.3.

Level 0 Balancing Requirement

All data flows entering or leaving the Level 0 system box MUST enter or leave the Level 1 DFD. Net input/output streams must be strictly preserved across levels.

Data Store Conventions

Data stores are identified by a 'D' prefix (e.g. D1 Users, D2 Orders). They represent data at rest (SQL database, file, cache). Processes write to or read from stores.

Flow Labeling & Transformations

Every arrow MUST be labeled with a noun representing data (e.g., "Order Info", "Receipt"). Processes MUST perform a transformation on input data to produce new output data.

Structure Chart Symbols & Couplers

○──> Data Coupler

Open circle arrow. Passes simple data values (e.g. customerId, amount) required for calculations.

●──> Control Coupler

Filled circle arrow. Passes flag/boolean parameters (e.g. isValid, EOF) that alter program execution flow.

◆ Junction Conditional

Diamond at base of parent module. Indicates a module is called conditionally under an IF-statement.

⟳ Curved Arrow Loop / Iteration

Curved line across call branches. Indicates repetitive calls to child modules inside a loop.

Use Case Diagrams

Defines system boundaries, actor goals, and conditional relationship stereotypes.

graph LR Customer((Customer)) --> UC1(Checkout Order) Customer --> UC2(View History) UC1 -.->|include| UC3(Validate Card) UC1 -.->|extend| UC4(Apply Coupon)

Stereotype Rules: Include vs. Extend

<<include>> (Mandatory Sub-step)

Target use case is ALWAYS executed when base use case runs. Arrow points FROM base TO sub-step (e.g., Checkout ALWAYS includes Validate Card).

<<extend>> (Optional Condition)

Target use case ONLY runs under specific optional conditions. Arrow points FROM optional extension TO base use case (e.g., Apply Coupon extends Checkout).

User Stories & The 3 Cs Framework

Master Agile requirement specification, card structures, conversations, and acceptance criteria.

The 3 Cs Framework

1. Card

Written invitation to a conversation formatted as:
As a [role], I want [feature], So that [benefit].

2. Conversation

Collaborative discussion between developers, product owners, and QA to flesh out requirements and edge cases.

3. Confirmation

Acceptance criteria specifying verification rules formatted as Given / When / Then.

User Story & Acceptance Criteria Example

US-204: 1-Click Express Checkout Priority: High
"As a Registered Buyer, I want to save my default credit card, So that I can complete purchases faster without re-entering card details."
Acceptance Criteria (Confirmation)
Scenario 1: Valid Card Saved
GIVEN user is logged in with a saved card
WHEN user clicks "Express Checkout"
THEN order is processed immediately without prompting card details.
Scenario 2: Card Expired
GIVEN user's saved card expiry date has passed
WHEN user clicks "Express Checkout"
THEN system prompts error "Card expired, please update billing info."
